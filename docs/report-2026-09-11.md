# webimg improvement report — 2026-09-11

**Author:** the planning session Anton opened (Fable). **Status:** decided. Every decision
below is copied into `plan.md` §1 and is not reopened by build sessions.

Inputs: the full webimg source at commit `076a690` (15 passing tests), the bulk-ingest brief
for thingstodoinparaguay.com, the `webimg-pipeline` skill, and Anton's ask: *"help me use
webimg better and let me fix all images for my HTML/PHP and GitHub projects, locally or in
git repos."*

---

## 1. What webimg is good at today (do not regress)

- `npx --yes github:antonmarklundcom/webimg …` from any repo, local or cloud, no install.
- The Claude session names files (`--name`/`--alt`); no API key needed or wanted.
- `convert` / `batch` / `serve` / `zip` all share one core (`src/convert.js`), one manifest
  writer that merges by slug, and a dependency-free zip writer. The code is small and clear.
- Tests generate their own fixtures and pass offline.

## 2. What is wrong or missing, ranked by how much it costs Anton

| # | Finding | Evidence | Cost today |
|---|---|---|---|
| 1 | **No way to fix an existing site.** webimg only creates new image sets from a file you already chose. There is no command that scans a project, finds every `<img>`, and upgrades it. | `webimg.mjs` has only convert/batch/serve/zip | The actual ask ("fix all images in my projects") is impossible without hand work per image. |
| 2 | **Output shape is hard-coded to AVIF+WebP at 640/1280/1920.** No JPEG/PNG output, no `original`. Sites that render `webp + jpg` (thingstodoinparaguay, `src/View.php`) or 400/800/1600 (`Uploader::WIDTHS`) or 480/960/1600 (viaje.com.py) cannot use the default output. | `src/process.js` always emits `.avif` + `.webp`; no jpeg encoder path | Every consumer that is not a php-site-template site needs flags on every call, and there is no jpg at all. |
| 3 | **Per-project settings live nowhere.** Widths, out dir, quality, formats are CLI flags only. Three sites, three conventions, and the Claude session has to remember them every time. | no config file lookup anywhere | Wrong widths / wrong out dir are the most likely silent mistake. |
| 4 | **`@anthropic-ai/sdk` is a hard dependency at `latest`.** Every first `npx` run installs it although naming is the session's job. `latest` is also unpinned. | `package.json` deps | 30–60 s first run, larger install, an unpinned dep in a tool that is supposed to be stable. |
| 5 | **Upscaling is the default.** `withoutEnlargement: false`; a 1500 px source silently becomes a soft 1920 px file, with only a log line. | `src/process.js` | Soft hero images on the site; the skill tells sessions to "watch for ⚠ upscaling", i.e. a human has to notice. |
| 6 | **No idempotent rerun.** `batch` re-encodes every row every time. For 62 images × 6 outputs that is minutes per rerun and churn in git. | `runBatch` in `webimg.mjs` | Reruns after fixing one alt text re-encode everything. |
| 7 | **The manifest cannot carry the binding.** Extra CSV columns (e.g. `target_path`) are dropped by `normalizeRow`. There is no per-image `width`/`height`/`mime`, which a DB-backed site needs. | `src/batch.js`, `src/convert.js` | thingstodoinparaguay's importer would have to re-derive everything. |
| 8 | **`--prompt` is required even when `--name` and `--alt` are given.** | `requiredOption("--prompt")` | Friction and a dummy value on every call from a session. |
| 9 | **`<picture>` snippet has no `sizes` attribute and always assumes AVIF.** | `buildHtmlSnippet` | Browsers pick the 1920 file on phones; snippet is wrong for non-AVIF sites. |
| 10 | **`serve` cannot take a prepared list.** 62 files means typing 62 slugs and alts in the browser. | `src/ui.html` | This is exactly the tedium the brief worries about in option A. |
| 11 | No CI, no CHANGELOG, version stuck at 0.1.0, README is a flat wall. | repo root | Nothing blocks a broken push; sessions cannot tell what changed. |

## 3. Decisions on the brief (thingstodoinparaguay bulk ingest)

**Transport (Problem A):** solved by `webimg serve` on Anton's PC, plus the fix for finding 10
(load a prepared CSV so slugs and alts are pre-filled; dropped files are matched by filename).
Anton names his PNGs after the content slug (`asuncion-city-tour.png`), drops the folder,
clicks Convert, and gets one zip. Bytes never leave his machine.

- **B (hosted webimg on Vercel): rejected.** Every listed constraint is real (4.5 MB body,
  timeouts, sharp in serverless, no filesystem, untrusted decoding on a public endpoint) and the
  only benefit, "nothing to install", is already true of `npx`. It would also be the first
  webimg path where the images leave his machine.
- **C (wasm in the browser): rejected.** A second encoder to keep in sync with sharp for no
  gain over `serve`, which already runs in a browser on localhost.
- **D (git as transport with an Action): accepted as an opt-in extra**, not the main path.
  It is useful for the "GitHub projects" half of Anton's ask: an Action that runs `webimg audit`
  on every PR (report only) and, on demand, `webimg fix` on a branch. Not for 62 big PNGs.

**Output shape (Problem B):** webimg gets generic `--formats` (`avif`, `webp`, `jpg`, `png`,
`original`) and keeps `--widths`; both, plus `out`, quality and `sizes`, can live in a
`webimg.config.json` in the consuming repo (finding 3). So thingstodoinparaguay commits
`{"widths":[400,800,1600],"formats":["webp","original"],"out":"public/media"}` and every
call from any session is just `npx … batch . --manifest jobs.csv`.

- Q4 (teach the site AVIF instead?): **do both, but the site change is not this repo's work.**
  Adding `<source type="image/avif">` to `View.php` is a 5-line win and is recommended in the
  consumer doc. It does not remove the need for `--formats`, because the site's `<img>`
  fallback is JPEG/PNG and webimg cannot emit those today.
- Q3 (named profile vs generic flags): **generic flags + a per-repo config file.** Named
  profiles exist only as keys inside that file (`"profiles": {"cards": {...}}`, `--profile cards`).
  webimg itself never learns a site's name.

**Binding (Problem C):** `batch` passes every unknown CSV/JSON column through into the manifest
entry's `meta` object (so `target_path`, `lang`, anything). The manifest also gains per-entry
`width`, `height`, `mime`, `fallback`, `formats`, `widths`. That is everything a DB importer
needs. The PHP importer (`bin/import-media.php`) and the `cover:` front-matter key are
**thingstodoinparaguay's work**; this repo ships the exact spec and a paste-ready prompt for
that session in `docs/consumers/thingstodoinparaguay.md`. Recommendation carried into that
doc: do the `cover:` front-matter route, because a cover that exists only in SQLite is lost on
re-seed (the brief's latent bug is real).

- Q1: `serve` as it exists is enough for transport but not for 62 × slug+alt; finding 10 fixes it.
- Q2: no, a server buys nothing here. See B/C above.
- Q5: the 62-row manifest is authored by a Claude session **in the thingstodoinparaguay repo**
  (it knows the content paths), committed as `content/media-jobs.csv`. A `webimg audit` skeleton
  is not needed for that site (no images exist yet); for existing sites `audit` writes the
  skeleton (§4).
- Q6: yes, worth generalising, but only as far as the config file. Three sites = three
  10-line JSON files, zero site-specific code in webimg.

## 4. The new capability: fix an existing project

Two commands, one plan file, so the session still owns names and alt text:

1. `webimg audit [dir]` scans `.html .htm .php .md .jsx .tsx .vue .astro` (ignoring
   `node_modules`, `.git`, `vendor`, and the config's `exclude`), extracts every image
   reference (`<img src/srcset>`, `<picture><source>`, CSS `url()`, `og:image`), resolves each
   against the web root, and reports per image: missing file, oversize, legacy format without
   modern siblings, generic filename, no alt, no width/height, no `loading`, dynamic src it
   cannot follow, unreferenced originals. It writes `webimg-plan.csv` (one row per source
   image, with `name` and `alt` pre-filled where the existing markup is already good) and
   `webimg-audit.json`.
2. The Claude session edits the CSV: fills `name`/`alt`, sets `action` per row.
3. `webimg fix [dir] --plan webimg-plan.csv` converts every `convert` row with the project's
   config, rewrites each reference in place (`<img>` → `<picture>` keeping class/id/data-*
   attributes, alt from the plan, width/height/loading added), optionally deletes the originals,
   and is idempotent: rerunning on a fixed project changes nothing.

"Locally or in git repos" needs no special mode: clone, run, commit. For GitHub-only use,
`webimg init` writes the config file and an Action that runs `audit` on PRs (report only).

## 5. Everything else, decided

- Remove the Anthropic SDK from `dependencies`; load it lazily only when `ANTHROPIC_API_KEY`
  is set and it is installed. Keep the API path documented as optional. (finding 4)
- No upscaling by default: widths above the source width are dropped with one info line; if all
  are above, emit one file at source width. `--allow-upscale` restores the old behaviour. (5)
- `--skip-existing` on `batch`/`fix`: skip a row when every expected output exists and is newer
  than the source. (6)
- `--prompt` optional whenever `--name` and `--alt` are both given. (8)
- Snippet: one `<source>` per non-fallback format in the configured order, `sizes` from config
  or `--sizes` (default `100vw`), `<img>` fallback = last format at the middle width. (9)
- Add `.github/workflows/test.yml` (this PR), `CHANGELOG.md`, bump to 0.2.0 at release. (11)
- Skill delta for `webimg-pipeline` (Anton applies it to the synced skill after release): the
  "six files per slug" check becomes "every file listed in manifest.json"; document
  `webimg.config.json`, `audit`/`fix`, and that `--prompt` is optional.

## 6. What this repo does NOT do

- No hosted service, no wasm encoder, no `ANTHROPIC_API_KEY` requirement, no site-name
  profiles, no PHP code. The importer for thingstodoinparaguay is specified here and built there.
- No rewriting of dynamic PHP `src` expressions; those are reported, not touched.

## 7. Model split (see plan.md phase table)

Opus builds everything that others build on: the output/format contract, the config and
manifest contract, the audit plan-file contract, and the markup rewriter. Sonnet fills in the
UI, the git/Action templates, docs, and the release pass. All Opus phases run first, in order.
Estimated: 4 Opus phases ≈ $45–55, 4 Sonnet phases ≈ $20–25, ~5 h wall-clock with lane 2 in
parallel. Fable does not appear again unless Anton opens a review after the release pass.
